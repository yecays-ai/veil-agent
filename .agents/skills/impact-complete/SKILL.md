# 影响分析 → 联动修复 → 回归验收（每单必做）

本 Skill 结合成熟开源 [Superpowers systematic-debugging](https://github.com/obra/superpowers/tree/main/skills/systematic-debugging)、[verification-before-completion](https://github.com/obra/superpowers/tree/main/skills/verification-before-completion) 的“根因追踪、证据先于完成声明”实践，针对本仓库自主活动、记忆、桌面 UI 与后台调度的耦合做了通用化。不安装额外模型、服务或依赖。只读规则本身不能替代代码测试与 Windows 实际体验。

## 核心交付契约

**完成一个变更 = 新能力能用 + 原有受影响能力仍能用 + 发现的连带问题已在本任务中修好。**
- 本单改动导致任何已有场景失败、失效、假成功、静默退化、数据丢失或权限绕过：属于本单未完成，必须在**同一个分支/PR** 修复和复查，不把它当作“等 lan 发现以后开下一单”。
- 仅与本单毫无因果关系的既有独立问题才另记，不得以此名义拆出影响范围内的故障。
- 若修复涉及需要 lan 决定的产品方向、额外费用、删除数据或高风险操作，先给**可使用且保持旧功能**的方案并请求明确授权；不能悄悄取消旧功能。无法安全修完要暂停交付，报告阻断，不能合并或声称完成。
- Windows 真机仍只能由可用的实机环境和 lan 实际验证；自动测试通过只表明代码级证据，不能称真机验收完成。若真机未验收，明确标注“待 Windows 验收”，并完成开发者能够做的功能验证。

## 每次任务的必经六步

### 1. 明确使用效果与“不回退”的现状
写出用户做完能直接完成的事情。列出修改前至少一个相邻的真实使用行为、它原来如何工作；不以模块名称或 PR 改动文件代替用户旅程。

### 2. 搜索真实影响范围，不用固定功能清单替代思考
以要改变的**行为、数据、接口、状态、配置**为中心，主动搜：
- **谁调用/引用它**：入口、调用者、配置选择器、API、桌面事件、计划任务、脚本、其他角色；包括不同模式、后台和定时路径。
- **它调用/改变谁**：读写的数据、预算、缓存、记忆、通知、权限、外部程序、持久化、备份恢复、UI 与错误处理。
- **边界和组合**：启动/停止、空值/失败/超时/取消、升级/重启/切换、旧配置与新配置、并发、重复执行、不同角色与设备。
- 通过仓库搜索、调用图、入口代码、引用测试和 git diff 做**双向追踪**：向上追到所有使用者，向下追到所有副作用，横向查共用状态及共享配置。不要只读本次预计修改的文件。
- **项目功能会演进**：上述只是搜索方法，不是唯一要查的名单。每次根据真实代码画出本单的影响范围，发现新消费者继续扩展，直到每条路径有证据或明确未知。

### 3. 写出“影响-行动”矩阵，边查边扩展
在工单当前状态或 PR 描述记录：
| 受影响的使用场景 | 代码证据（调用入口→路径→结果） | 当前行为 | 改后预期 | 必须联动修改的地方 | 验证方法及状态 |
每条路径只允许三种结论：
- **已覆盖**：已修相关调用点，有通过的回归证据。
- **有依据不受影响**：给出具体代码/配置证据，说明为什么不受影响。
- **阻断/未验证**：说明无法保证的具体行为；影响正确性、隐私、安全或数据的情况不能带着它宣称交付完成。
未知范围不准随手写“无影响”，也不准仅以“CI 全绿”“只有一个文件”判定安全。

### 4. 同单修全联动，不以“严格按需求”漏修
从用户的完整日常流程安排最小必要变更，覆盖被发现的真实消费者与共享状态。比如添加一个仅支持聊天的通道，必须追查所有共用模型选择器的调用链，**让原有其他工作继续可用**，而不是把那些报错称为“功能尚未规划”。检查跨路径的权限、成本、数据一致性；如果需要改多个文件，就在同一 PR 内完成，避免留下半实现。

### 5. 对变更前后的真实使用旅程做验证
- 为新增行为、相邻旧行为、切换/恢复、拒绝/失败/停止写具体回归案例；能自动化的，用假模型与假数据做集成回归，不只测局部函数。
- 执行新旧相关测试、项目已有 CI 检查；读取退出状态和失败原因。已知旧失败与新失败分开报，不把“有测试文件”当作通过。
- 对 PR 最终 diff **重新做步骤 2–3**，保证实际修改没有产生新的影响路径；处理实质审查问题后再做一次。
- 按“lan 从 Windows 打开什么、点什么、看到什么”写验收。可以提前自动证明的不要让 lan 才来发现；无法在当前环境进行的真机验证明确保留待验状态。

### 6. 合并门槛
本次变更导致的已知功能故障、回归、未经批准的功能退化、权限/数据风险 **一项未解决就不要合并**。要提交的 PR 必须带影响-行动矩阵与证据；同 PR 更新 STATUS.md、HANDOFF.md，分别记录自动验证和真机验收状态。审查只追实际故障与风险，不做无意义风格返工。

## 发现自己正漏检的信号
- “用户只说了聊天，所以自主活动坏了不属于这单。”
- “等用户自己测试出来，再开单修。”
- “代码只改了一个函数，所以应该不影响其他地方。”
- “新功能能跑一次/测试全绿，代表完整体验完成。”
- “先上线再看报不报错。”

遇到这些说法，停止完成声明，返回步骤 2，补查所有消费者；找到相关回归就在当前 PR 修复。

## 本仓库已知案例（用于检验流程，不是固定检查清单）
工单 228 只支持 CC 聊天。实际调用路径：
`autonomy.py` 的自主活动调用 `chat.send(..., autonomy=True)` → `veil_agent.py` 默认使用当前聊天 provider → `_claude_agent_chat` 收到 autonomy 直接拒绝。这意味着“聊天选 CC”连带破坏了既有自主活动。没有独立模型选择与正常回退之前，不能把工单 228 的整体兼容性声称为已完成；此 Skill 不会自动修复正在运行的代码。
同样的思路应检查将来**任何**代码改动涉及的消费者、共享状态和用户旅程，而不是只列自主醒来、瞄一眼等固定几个功能。
