# PR 审查

## 1. 先对照工单与类型

- 类型是功能开发 / Bug 修复 / 专项审计 / 纯文档维护？按 `AGENTS.md` §2 检查该做的步骤有没有做。
- PR 是否只做了工单里写的，验收步骤能否做到。多做的部分要求删掉。
- 纯文档维护单：只核对事实、链接与编号，**不请求 AI 审查机器人**，也不因风格评论反复改。

## 2. 自己读一遍改动，重点看

- 会不会坏功能、卡死、取消后状态错乱。
- 记忆、聊天、配置会不会丢或被覆盖。
- 花费上限能不能被绕过，请求会不会重复发。
- 有没有提交密钥、人设正文、真实聊天、本机绝对路径；工具有没有越权；一个角色能不能读到另一个角色没分享的记忆。

## 3. 审查器分工

| 审查器 | 用途 | 触发方式 |
| --- | --- | --- |
| Cubic | 默认功能审查 | 在 PR 中请求审查 |
| CodeRabbit | Cubic 额度耗尽或长时间无响应时接替 | PR 评论 `@coderabbitai review` |
| Sourcery | ① 普通 PR 审查（代码质量与安全规则）；② 安全告警核实 | 已有扫描结果 + 逐条核实，结论写「真实漏洞 / 条件性风险 / 误报」；不擅自关告警或改扫描配置 |

- **切换**：同一 PR 不反复触发多个审查器空转；换审查器时在 PR 里写一句为什么换。
- **集中修复、一次推送**：同一批实质问题一次性改完、一次性推送，不边改边推、不为单条评论反复触发 CI；格式/风格评论忽略或一句说明。
- **交叉复审**：涉及数据写入、权限、预算、密钥、删除的 PR，建议换另一个审查器再看一遍，结论写进 PR 评论。
- 只修上述实质问题；其余在原评论下简短说明原因并标记已解决。不追风格建议。
- Cubic/Rabbit 的评论与 `COMMENTED` review **不是** required status check，也不等于批准；合并门禁只认仓库实际保护规则。

## 4. CI 与合并边界

- CI 红了先修，只认最新提交的必需检查。
- 实质问题修完、必需 CI 通过后，**把 PR 交给 lan**：说明改了什么、CI 结果、验收步骤，然后暂停。
- 只有 lan 明确说合并才合并；她说自己合就停手。不直接推 `main`，不绕过保护，不改审查平台配置。
- 合并后清理本次任务创建的 worktree：确认无未提交修改，有就保留并报告；不碰正式运行目录、其他 Agent 的 worktree 和别人的交付。

## 5. 写结论

审查结论写在 PR 评论里：能交付 / 还要改什么（逐条，带文件位置）/ 哪些意见不采纳及原因。合并后请 lan 按 `docs/ACCEPTANCE.md` 对应条目体验，通过后回填清单与工单。
