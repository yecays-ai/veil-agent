# VEIL Agent：系统接入与完整交付

与 `impact-complete` 分工：
- `impact-complete`：检查改动有没有破坏已有功能。
- `integration-complete`（本文件）：检查新增能力是否真正接入完整使用流程。

**原则：思考覆盖整体，施工保持最小，验收贯穿实际使用，交付以用户获得的能力为准。**

## 一、开工前

1. **先确认目标没有偏差。** 工单字面写的是技术动作（例如“浏览器连续执行”），但 lan 真正要的是一个能力（例如“Peter 能在后台自己做研究”）。先问：用户做完这件事后到底要获得什么？工单写的做法是不是最短路径？有偏差就在开工前说出来，不要只盯着技术实现。
2. **查现有实现和可复用模块**（`reuse-first`），尤其是已有的统一层：权限、预算、停止、日志、运行状态。优先复用，不得为局部功能另建平行的权限、预算、停止、日志或执行机制；确需新建，先报告 lan 并说明现有的为什么不行。
3. **八项接入评估。** 逐项写：适用吗 → 现有实现在哪 → 必要改动 → 怎么验收；不适用写原因，不得无理由遗漏。

| 项 | 要问的 |
| --- | --- |
| 入口 | 聊天、自主醒来、定时、界面、其他通道、其他角色，哪些会用到它 |
| 停止与恢复 | 按停止、崩溃、重启、中断后“继续”时它的状态对吗 |
| 权限 | 每个真实副作用是否经过 VEIL 统一的允许/询问/禁止，由程序而不是提示词控制 |
| 费用 | 计入总账和每日上限吗，超了怎么停 |
| 数据 | 存哪、属于哪个角色、备份恢复管不管、删除时留不留 |
| 状态可见 | lan 能看到它在做什么、花了多少、为什么停吗 |
| 升级回滚 | update.bat 之后还能用吗，版本是否固定，配置怎么迁移，坏了怎么退回 |
| 真实环境 | Windows、Docker、打包后的桌面版是否真的跑过 |

## 二、全面检查，不等于全面施工

八项都要考虑，**只有相关项才需要实际接入和验收**。例如按钮只是切换一个本地页面，就不要为此重测 Docker、模型费用、崩溃恢复。检查覆盖整个用户操作链路，施工和验收只针对本次功能相关部分，不得以全面性为由无限扩大范围。

## 三、交付

功能完成以真实用户场景通过为准，不以代码提交、单元测试或 PR 合并为准。涉及停止/恢复的功能，验收要走一圈：开始、中途停、重启、继续、出错。

## 四、发现缺陷时

1. 先判断根因及其可能影响的同类路径，优先修共同原因，不只修表面症状。
2. 同类问题重复出现两次仍未解决，或连续修复不断暴露新的跨模块衔接问题时，**重新检查原来的接入设计**：
   - 是否存在共同根因？
   - 继续局部修复是否仍然合理？
   - 是否需要调整原工单范围？
   复查后决定继续最小修复还是调整方案；不自动开新工单，不自动重构，不重复已通过的验收。
3. 会造成功能失败、安全风险、数据损失的问题优先处理；其他优化不阻碍当前交付。
