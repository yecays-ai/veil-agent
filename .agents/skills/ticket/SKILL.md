# 工单流程

## 0. 先判类型

| 类型 | 走哪些步骤 |
| --- | --- |
| 功能开发 | 全部步骤 + `integration-complete` 八项评估 |
| Bug 修复 | 全部步骤 + `systematic-debugging`（可省 `integration-complete`） |
| 专项审计 | 步骤 0–3、5（只产出报告）、10；不请求 AI 审查 |
| 纯文档维护 | 步骤 0–3（工单可省，直接分支/PR）、5（只改 md）、10；不请求 AI 审查 |

判定不清按更严格的一类走，并在 PR 里写明理由。规则原文见 `AGENTS.md` §2。

## 1. 开工

拉取最新 `main`；读 `docs/PRODUCT_PREMISE.md`、`STATUS.md`、`HANDOFF.md`、`docs/ACCEPTANCE.md`；核对上一张相关工单的 **PR 状态、合并提交、最新 CI、是否已部署、是否有验收记录**（五项分开记录）。在独立 worktree 工作，不碰正式运行目录。用两句话向 lan 复述目标。

## 2. 过三问并确认格子

答不上「做完她每天能多做哪件事」「比最简单的替代多了什么」「她不看代码怎么验收」就不开工；同时对照 `docs/PRODUCT_PREMISE.md` 确认属于 A/B/C/V/D 哪一格。

## 3. 先查复用

按 `reuse-first` 查两处：仓库里已有的审计/调研/设计（`docs/reports/`、`docs/tickets/`、`config-audit/`、`交付/`、`待办方案/`），以及外部成熟实现。已有的结论直接复用，只核实基线、是否被推翻、缺哪块。

## 4. 查全影响

执行 `impact-complete`；修 Bug 用 `systematic-debugging` 找根因；新功能/工具/通道另做 `integration-complete` 八项。凡本次变更造成的相邻功能回归，必须在**同一个 PR** 修完并回归验证。

## 5. 写工单 `docs/tickets/<编号>-<短名>.md`

只写四段（纯文档/审计单可只写目标与交付物）：

- 开头三行：属于哪一格；做完 lan 能多做的一件事；她怎么验收。写不出来不开工。
- 目标：一句话。
- 当前状态：现在缺什么、相关文件在哪、复用了什么。
- 验收步骤：lan 在 Windows 上做的 1–3 步体验，不写「跑测试」。

编号接着最大号往下排；**工单号与 PR 号不是一回事，引用时写全**。

## 6. 开分支并实现

从最新 `main` 开 `ticket/<编号>-<英文短名>`，一单一分支一 worktree。实现围绕工单目标完成全部联动修改；测试用假模型、假数据。提交前跑新旧相关测试，按最终 diff 复查影响路径。

## 7. 开 PR

用 `.github/PULL_REQUEST_TEMPLATE.md` 填全（类型、格子、影响矩阵、接入评估、根因、验收步骤、检查项）；把 `STATUS.md` 改成这张工单进行中的样子一起提交。

## 8. 处理审查

按 `pr-review`：默认 Cubic，额度耗尽换 CodeRabbit，安全类用 Sourcery 核实；只修实质问题。纯文档与只读审计单不请求 AI 审查，只跑 CI。

## 9. 提交后暂停

**PR 打开、CI 有结果后停下**，把 PR 链接、CI 结论、验收步骤交给 lan，等她说合并。她没明确说「合并」就不合并；她说自己合就停手。不直接推 `main`，不绕过分支保护。

审查意见集中处理：同一批实质问题一次改完、一次推送，不为单条评论反复触发 CI。

## 10. 请 lan 验收并回填

合并后告诉她验收步骤。新增待验收项写进 `docs/ACCEPTANCE.md`；她确认通过后在那里打勾、写日期，并回到工单补一行验收记录。她发现问题就开新工单修；没通过就是没完成。

## 11. 收尾

按 `handoff` 更新 `STATUS.md`（每个 PR 必须）与 `HANDOFF.md`（窗口结束或换人时）；写明部署状态与验收状态，不把「已合并」写成「已验收」。

合并后清理本任务创建的 worktree：确认无未提交修改，有就保留并报告；不碰正式运行目录、其他 Agent 的 worktree 和别人的交付。

同一个问题修两次还坏：停下报告。一张工单超过一小时：判断要不要继续，然后告诉 lan。
