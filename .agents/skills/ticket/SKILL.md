# 工单流程

0. **开工**：拉取最新 `main`，读 `STATUS.md`、`HANDOFF.md`，核对上一张相关工单的 GitHub PR 状态、合并提交、最新 CI 和实际交付；若已合并但 `STATUS.md` 仍显示施工中，在本 PR 中纠正。分别记录合并、自动检查、Windows 体验验收。用两句话向 lan 复述当前目标和你要做什么（`AGENTS.md`“开工和收工”）。
1. **过三问**（`AGENTS.md`），并对照 `docs/PRODUCT_PREMISE.md` 确认属于哪一格。任何一问答不上来，停下，告诉 lan 原因。
2. **先查复用**：按 `reuse-first` skill 查有没有成熟实现。
2.5. **查全影响并承担联动修复**：执行 `impact-complete` skill；修 Bug 按原版 `systematic-debugging` 查根因，完成前按原版 `verification-before-completion` 取得新证据，双向搜索要修改的代码、配置和状态的所有消费者及副作用，列出真实使用旅程。凡由本次变更造成的相邻功能回归，必须在**同一个 PR** 修复、回归验证；不能留给 lan 发现后再开新单。
2.6. **新功能/新工具/新通道做接入评估**：执行 `integration-complete` skill，先确认工单字面没有偏离 lan 真正要的能力，再对八项逐项判断适用性；只有相关项才施工和验收。
3. **写工单** `docs/tickets/<编号>-<短名>.md`，编号接着最大的往下排。只写三段（新功能/工具/通道四段）：
   - 开头三行（`docs/PRODUCT_PREMISE.md`）：属于哪一格（A / B / C1 / C2 / C3 / V / D）；做完 lan 能多做的一件事；她怎么验收。写不出来不开工；同一格上一张工单没经 lan 验收通过，不开同一格的下一张（为跑通同一条完整场景必须一起施工的前后端接线除外）。
   - 目标：做完 lan 能做到什么（一句话）。
   - 当前状态：现在缺什么，相关文件在哪。
   - 验收步骤：lan 在 Windows 上做的 1–3 步体验，不写“跑测试”。
   - 接入检查（仅新功能/工具/通道）：八项里相关的几项各一行，写现有实现和验收方式；其余写“不适用”及原因。
   不写被否决的方案和过去的误会。
4. **开分支**：从最新 `main` 开 `ticket/<编号>-<英文短名>`。一张工单只用这一个分支。
5. **实现**：围绕工单目标完成必要的全部联动修改；测试用假模型、假数据。提交前跑新旧相关测试，并按 `impact-complete` 以实际 diff 复查全部影响路径，并按 `verification-before-completion` 核查执行结果，补齐回归。
6. **开 PR**：PR 描述必须包含 `impact-complete` 影响-行动矩阵及回归证据；发现由本 PR 引起的连带故障则先在本 PR 修复，不准留待用户验收后另开单。用 PR 模板，标题说清楚改了什么；把 `STATUS.md` 的“现状/下一步/验收”改成这张工单进行中的样子，一起提交。
7. **处理评审**：按 `pr-review` skill 请求并处理 Cubic 审查；只修功能、用户使用、数据完整性、隐私和安全方面的实质问题。Cubic 的评论或 `COMMENTED` review 不自动成为 GitHub required status check。
8. **合并**：Cubic 审查完成、当前 PR 最新提交的必需 CI 通过、该修的实质问题已处理，并满足 GitHub 实际分支保护后，agent 用 GitHub 合并，不等 lan。不得把评论当成 required check，不得绕过保护或直接推 `main`。
9. **请 lan 验收**：合并后告诉她验收步骤。她发现问题就开新工单修；没通过就是没完成。同一个问题修两次还坏，停下报告。
10. **收尾**：按 `handoff` skill 更新 `STATUS.md`（每个 PR 必须）和 `HANDOFF.md`（窗口结束或换人时），记录检查和体验证据。没更新 `STATUS.md` 的 PR 不算完成。

做了一个小时还没完：判断要不要继续，然后告诉 lan。
