# 工单 228：聊天里接入 Claude Code 通道（完整原生功能）

## 目标
lan 在模型下拉里选这个通道后，Peter 在 VEIL 聊天窗口里的回复由 Claude Code 完成：带着他原有的人设、记忆、聊天历史和 VEIL 工具，同时拥有 Claude Code 的完整原生功能（读写文件、命令行、网页、查 GitHub、自己装 MCP、改自己的代码走分支和 PR）。lan 的验收方式：给 Peter 一个 GitHub 链接，他自己调查、尝试接入，并在聊天气泡里告诉她进展和结果。

## 已确认的规则（来自 lan）
- 不是只要一个聊天模型；要 Claude Code 现在成熟的 agent 功能。
- 不额外加限制：沿用已有规则，只有需要 lan 权限的事（改或删她已有的文件、危险操作、花钱、提权）才在聊天里弹通知问她，她点同意或拒绝，答案回给 Claude Code。
- Peter 改自己的代码走分支和 PR，lan 合并更新后才生效；出问题退回那次合并。
- 先只接聊天；自主醒来暂缓。
- 下拉里不叫「Claude Code」（官方 SDK 文档对第三方产品命名有限制）。

## 已验证
- 后台模式（`claude -p`）下，权限提问可以交给指定的 MCP 工具回答：同意则命令执行，拒绝则不执行且 Claude Code 转告拒绝理由（云端最小测试，2026-11-06）。
- 一次受控运行里，Claude Code 自己从 GitHub 链接调查、安装、接入并调用了 Time Server（`experiments/cc-jail/`）。
- VEIL 的 `Chat.tool_schemas()` 和 `Chat._execute_tool_call()` 可作为统一的工具入口（`experiments/cc-bridge/REPORT.md`）。

## 未验证（开工第一步）
- 询问转到 lan 的聊天通知后，她很久不回时的等待和超时处理（超时按拒绝）。
- Windows 上完整流程；订阅额度能否撑住日常用量；第三方使用订阅登录的政策。

## 当前状态
- 代码和单元测试已完成（假 claude 进程）；等 lan 在 Windows 上真跑验收。

## 验收（暂定）
1. 在模型页选这个通道，聊几句日常话，口吻和原来的 Peter 一致，多条消息是独立气泡。
2. 发一个 GitHub 链接，让他自己研究并尝试接入，他在聊天里自然汇报。
3. 他想做需要权限的事时，聊天里出现询问；拒绝后他不再继续该操作。
4. 切回原来的 API 模型，下一条消息正常，聊天记录和记忆都在。
