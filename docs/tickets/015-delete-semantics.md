# 工单 015：统一记忆删除行为

## 目标

`/forget`、`/restore`、`/delete` 行为清晰一致：**`/forget` 可恢复，`/delete` 不能用普通命令恢复**，删除意图不会被程序意外撤销。

## 决策核对（原文证据）

- 005g（lan 2026-10-19）：“她在手机版 VEIL 里的规则是‘删除就是忘记’”，要求 `/delete` 一次一条、二次确认，且“本程序也不提供 `/restore` 恢复已删除的记忆”。README 同样写 `/delete` “也不能 `/restore`”。
- 009 的工单正文写“隐藏或删除……确认后可恢复”和验收 3 “`/restore` 后两者都能重新出现”，但它是 Codex 写的实现工单，**没有找到 lan 明确批准改变删除规则的原话**；STATUS 里的“`/restore` 恢复”验收只记录她试过恢复，没有说删除可以恢复。
- 本工单由 lan 2026-10-20 明确提出：没有相反证据就按 005g 统一。因此以 005g 为准，009 里与之冲突的两处已改。

## 现状（改之前）

`memory_agent.py` 的 `/restore` 对已删除的记忆会调 Ombre `trace(restore=True)` 并取消隐藏，等于能撤销删除；两个测试文件把“删除后恢复成功”当作通过条件。

## 改了什么

- `/restore` 对已删除的编号只回一句说明，不调用 Ombre，不改任何状态；`/forget` 隐藏的照常 `/restore`。
- `/delete` 的确认提示和完成提示都说明：不能用 `/restore` 恢复；Ombre 只做软删除，文件仍在记忆目录里，没有被物理擦除，本程序不再读取或想起它；只想暂时不想起请用 `/forget`。
- Ombre 没确认删除时，本地仍标记为已删除并屏蔽，提示可重试 `/delete 编号`。重启后屏蔽仍在（状态文件保存），不触碰 Ombre 记忆库，也不自动清理。
- 测试：删除后 `/restore` 被拒绝且不调用 Ombre；删除后 Peter 的搜索和更新都碰不到它；隐藏→`/memory` 显示（已隐藏）→恢复；Ombre 失败后重启，隐藏和删除仍然屏蔽、其他记忆都在、重启不产生 Ombre 调用。
- 文档：009 工单两处恢复表述改为只适用于 `/forget`；README 补软删除说明。

## 不做

物理彻底擦除、批量删除、记忆库迁移、给 Peter 删除工具、重写 Ombre、删除旧 extract 代码。

## 验收步骤（lan 在 Windows 上做，用测试记忆）

场景 A：对测试记忆 `/forget 编号` 再确认 → 不再被想起，`/memory` 显示“（已隐藏）”；`/restore 编号` 后可再检索。
场景 B：对另一条 `/delete 编号` 再确认 → 提示说明软删除、不能 `/restore`；`/memory` 不再列出，Peter 搜不到；`/restore 编号` 被拒绝并说明原因。
场景 C：重启 Peter，A 的恢复和 B 的删除都仍然有效；其他记忆正常。（Ombre 调用失败的情形已由自动测试覆盖，真实环境不易制造。）
