# 387 时间与自主活动的连续性（第一阶段）

属于 A（陪伴核心）。Lan 离开一段时间回来时，Peter 能知道间隔和自己期间记录过的活动；自主醒来也能看到她上次发言的时间，而不推断她是否在睡。验收：用真实聊天和自主消息观察他是否自然接上，不把已睡完的人再次催去睡，也不机械汇报。

## 已批准的范围

- F1：给模型的聊天历史中，间隔至少一小时的消息之间标注时间；自主消息标注发送时间。界面和聊天记录不改。
- F2：按最后一条未撤回的用户消息独立计算间隔，主动消息不会重置；聊天超一小时以及每次自主醒来都提供时间事实与最近用户话语。回来后前三个聊天请求保留当时的间隔事实，避免第二句指出错误时丢掉刚经过的时间；不推断用户状态。允许自然说出具体时长，不必每次提时间。
- F4：回来后的前三个聊天请求，按用户离开到回来的时间筛选自主活动记录，最多 300 字；之后不再注入，避免长期重复。分别标注有工具证据的动作、当时未完成的重点、失败或中断、下一步计划；决定本身不当成完成证据。超出的可用 autonomy_history 查；重新生成按原用户消息时间计算。
- 根据 Lan 现在的要求，自主唤醒的消息提示明确可以自然交流，无需汇报；保留工具权限、现有醒来设置和三条程序上限。F5 其他工作及 F6 相关记忆，等第一阶段真实体验验收再做。
- 不改人设、不做睡眠检测、不延迟主动消息；复用聊天时间、自主记录、原有上下文和工具，不引入依赖，不增加模型调用。

## 影响范围

| 场景 | 处理 |
| --- | --- |
| 普通聊天、自主醒来 | 同一时间计算，不按消息内容判断睡眠 |
| 主动消息、撤回、跨日 | 主动消息不重置用户时钟；撤回用户消息不计；时间转换到本机时区 |
| 回来后、重启和重新生成 | 从已有记录计算，重新生成以原消息时间为界；活动摘要最多进入回来后的前三个聊天请求 |
| 上下文不足 | 先丢活动摘要再裁历史；用户离开时长留在必要上下文 |
| 费用、数据、权限 | 不新增模型调用或数据文件；权限和日程不变 |
| 其他渠道 | 桌面及移动网页走同一聊天入口；QQ/邮件交付路径仍需实际验证 |

复用既有 `life_state.gap_text`、自主活动记录和 `autonomy_history`；原方案已经调查 SillyTavern 的时间宏，项目本身已有所需记录和上下文，故不引入新库。

## 验收

用实际场景检查：离开数小时、期间有多条主动消息，再回来时看 Peter 是否知道间隔、自然接上实际做过的事；直接问多久时能回答数字；连续聊天不反复报时或汇报；自主活动可自行做事、联系 Lan 或休息。测试重新生成、撤回、跨日和模型切换。真实模型对比与 Lan 日常体验尚未运行，弱模型可能仍忽略时间或产生报告腔，须如实记录。
