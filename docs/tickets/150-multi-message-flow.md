# 工单 150：连发几句时 Peter 等她打完，回复中途的新消息同一轮接上

分支：`ticket/150-multi-message-flow`。Claude 实现。

## 起因（Lan 2026-10-28 反馈 + 她的本机记录）

「我每次发多条消息，他那边回复都很怪……他是一句话一句话的这样单独回。」

- `message-processing.jsonl` 显示 18:18 之后几乎每条消息都单独成一批：消息一到立刻开一轮，DeepSeek 4–6 秒回完，下一句还没发出。例：22:03「我的意思是」→ 他先回了一大段，再回「等我说完」。
- 「Lan is typing.」只在本轮开始那一刻判断，那时输入框刚清空，几乎从不成立。
- 他回复途中 Lan 发的消息，只在「还要继续用工具」的步骤之间并入；他用 `done`、`stay_silent` 或直接写正文结束时，新消息被留到下一轮，于是先接着说旧话题再单独回新消息（例：22:00「等一下 / 为什么你是gemini / 我的钱！！」）。

Lan 选择：打字时他等你（像以前的小手机），但不要固定等待时间。

## 改动

1. **按真实打字状态等待**（`web_agent.py`）：消息到达后先留约 2 秒让她的下一次按键到达；只要她 4 秒内还在敲键就继续等；她发出下一句会重新计时；她停手或草稿放着不动，他就开始，把这几句一起交给他。最多等 90 秒（只防输入状态卡住）。请求回复、斜杠命令不等。桌面输入框打字时每秒报一次「还在输入」。
2. **本轮结束前接上新消息**（`veil_agent.py`）：他 `done`、`stay_silent`、第 10 条消息或直接写正文结束时，若 Lan 已发来新消息，本轮继续，新消息交给他；他写的正文先作为一条消息显示。reply_later 和 Lan 叫停时照常结束。
3. 插话后他写的正文不再被当作「复述之前气泡」而吞掉。
4. 一次性英文通知（`typing_wait_150_announced`）。

不往他的话里加任何风格提示；回不回、怎么回仍由他决定。费用：连发几句合并成一次请求，请求数只会减少。

## 验收（update.bat 之后，桌面 exe 需重新打包）

1. 连着发两三句（每句之间接着打字），他等你发完再回，回的是整体意思，不是一句一句回。
2. 只发一句、不再打字，他约 2 秒后开始回。
3. 打了半句停下不动，他几秒后照常回，不会一直卡住。
4. 他回复途中你再发一句，他在同一轮里接上，不会先把旧话说完再单独回一遍。
5. 让他已读不回后你再发一句，他会重新考虑要不要回。
