# 工单 007：Peter 自己调用 Ombre 工具来记（替换后台补记层）

**只准备，不实施。** 前提：工单 006（工具调用）已合并，并通过 lan 验收。

## 目标

Peter 像 Ombre 原生设计的那样，**自己判断**什么值得记、自己调用 Ombre 的工具保存、查找、更新；尽可能移除我们自写的后台补记层。lan 的体验不能比现在差：

- 自己判断保存，不用说“记住”；无价值的内容可以不记。
- 保留事实和原因，不是只存标签。
- 同一件事有新信息时更新、合并已有记忆，不重复。
- 保留共同经历和关系的发展。
- Peter 知道自己是 AI：讨论他自己的记忆、能力、权限、共同升级，这类有意义的讨论必须可以保存。

验收基线是 VEIL 旧仓库（`yecays-ai/veil`，`lib/memory/maintenance-input.ts` 等）已经实现的自主记忆行为，不是新发明的标准。

## 现状

读源码得到（Ombre 固定提交 `115d831`，没有运行）：
- Ombre 的原生用法是模型自己调工具：开口前 `breath()`，中途 `breath_search`，记事用 `hold`（一件事）或 `grow`（一段长内容，自动拆 2~6 条）；打标签、同一事件合并、写原因、软删除（`trace`）、隐藏（`trace dont_surface`）都是 Ombre 自己做的，005f 已打开它的模型。
- Ombre 没有“从聊天后台自动提取”的原生功能；历史导入只新建桶，不和旧桶合并，不适合持续使用。

我们现在的做法（`memory_agent.py`，主要在 005b / 005d）：每 4 轮后台补记一次——自写提示词、JSON 解析、逐字原话核验、把已存 40 条塞进去去重、读本机人设、丢弃候选日志。它存在，是因为 Peter 目前没有工具调用。

未验证（本工单必须先查清）：
- DeepSeek 在 lan 的配置（思考模式）下工具调用是否稳定，尤其是同一轮多步和 `reasoning_content` 的回传。006 要先验这个。
- Peter 自己会不会该记时记、不该记时忽略，会不会漏记或乱记。
- 每次 `hold` 的费用（一次工具步骤加 Ombre 自己的模型调用）和现在“每 4 轮一次补记”相比，哪个高哪个低。

## 保留不动

角色记忆隔离、`/memory` `/forget` `/restore` `/delete`、预算和 `/cost`、每轮自动召回、长对话裁剪。

## 做法（分阶段，旧代码最后才删）

1. 006 合并并验收后，先在真实对话里确认 DeepSeek 工具调用稳定；不稳定就停下告诉 lan，不继续。
2. 通过 006 的权限闸门，只给 Peter 一张 Ombre 工具白名单（读写记忆需要的那几个）；删除类操作仍由 lan 的 `/delete` 管，不给模型。
3. 新方案和旧补记层并存、可切换，用真实对话和下面的验收步骤对照；达到标准后，**再**移除旧补记代码和对应测试、文档。
4. 记忆库本身（Ombre 的 Markdown）不动；只处理我们自己的 `state.jsonl` 的迁移。

## 费用

先实测一段真实对话的请求数和估算费用，写进 PR；**任何降低记忆质量、减少调用的取舍先问 lan，并写明每天多/少多少钱**。

## 不做

不改 Ombre 源码；不做新记忆功能；不在 006 通过前动旧补记层；不在新方案达标前删除旧代码；不扩大到 Ghost、主动联系、语音。

## 验收步骤（lan 在 Windows 上做，同一批真实对话分别用旧方案和新方案对照）

1. 正常聊几件有原因的事（你喜欢什么、为什么；发生了什么、你们的感受），不说“记住”：`/memory` 里能看到他自己记下的条目，带事实和原因，不是只有标签；闲聊和玩笑没被记。
2. 对同一件事补充一个细节：原条目被更新，不是多出一条重复的。
3. 和他讨论他自己的记忆、能看到什么、权限、下一步升级：这类讨论被记成一条完整的共同决定。
4. 隔几天或重启后再聊到这些事：他自然想起来，包括之前的原因和你们的经历。
5. 屏幕每次保存或更新都有一行；`/forget`、`/delete` 照常可用；`/cost` 里能看到记忆相关的花费，和旧方案的对比写在 PR 里。
6. 对照旧仓库 VEIL 的行为：该记的记、该忽略的忽略，没有明显更差；更差的地方列出来由 lan 决定要不要继续。
