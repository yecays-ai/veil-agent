# 工单 205：费用账本增量读取（PERF-01）

## 目标

费用记录越来越多（长期运行后可达数万行）时，发送聊天、瞄一眼、自主唤醒前的预算检查不再因为每次都从头解析整本账本而变慢。

## 现状与做法

每次预留、结算、分类预算检查都会全量读取并解析 `costs.jsonl`，期间还持有预算锁。审计数据（6 万行）：单次约 0.70 秒。

做法（没有找到需要引入的现成库，改动在 `veil_agent.py` 内）：

- `Store.incremental_state`：只解析上次读取之后新追加的字节；文件被替换、截断、被修复/恢复工具改写，或长度不变却被改过时（文件身份、开头和结尾指纹、修改时间变化）自动整本重读。末行不完整仍按损坏处理并给出原有的修复提示。
- `_LedgerTotals`：按请求 id 增量维护今日、本月、未结算和分类（自主/瞄一眼）合计；同一 id 后出现的记录替换先前记录，与原来整本计算的结果一致。末行有效但没有换行这种少见情况回退到原来的整本计算。
- 原账本文件不变，格式不变；预留、结算、恢复对账、待核实暂停机制不变。

## 实测（假数据，本机 Python）

| 账本行数 | 原整本统计 | 现在 |
|---|---|---|
| 1 万 | 10 ms | 0.05 ms |
| 3 万 | 33 ms | 0.04 ms |
| 6 万 | 87 ms | 0.04 ms |

（审计机上整本读取含解析约 0.7 秒；这里只对比统计这一步，首次启动仍需读一遍账本。）

## 验收步骤

1. 更新后正常聊天、让 Peter 自主活动一轮；`/cost`（或预算页）显示的今日、本月花费与更新前一致。
2. 在复制出来的假数据文件夹上，往 `costs.jsonl` 末尾手工加一行乱码：再次发消息应被拦住并给出修复提示（与以前一样）。
3. 不要在真实 `costs.jsonl` 上做第 2 步。
