# 工单 012：让 DeepSeek 的缓存能命中（发送顺序 + 历史成块裁剪 + /cost 显示命中率）

## 背景

DeepSeek 对“请求开头一字不差相同”的部分按缓存价计费（本项目配置：缓存 ¥0.04/百万 token，普通输入 ¥2/百万）。账本（`Budget.settle`）早就按缓存价算；但发送顺序让缓存几乎命中不了：当前时间和花费账本写在人设后面，每轮召回的记忆插在历史之前，历史窗口满了以后每发一条就丢一轮最旧的，请求从人设之后的位置开始每次都不同。

## 做了什么

1. **发送顺序**：`[人设, 固定说明, 历史……, 召回的记忆, 能力变化记录, 当前时间和花费账本, 这条输入]`。固定说明（身份、能力、记忆和工具说明）不含时间和账本；会变的内容都放到历史之后。`/self` 显示的仍是实际发送的全部说明（固定部分 + 变化部分）。
2. **历史成块裁剪**（`history_keep`）：历史窗口满了以后，一次丢掉最旧的一小块（`history_rounds // 4`，默认 20 轮时是 5 轮），而不是每条消息丢一轮。窗口起点因此几条消息不变，缓存才命中得了。仍然不会超过 `history_rounds`；平均少带约两轮原文，更早的聊天照旧在本机保存，长期记忆不受影响。`history_rounds` 小于 8 时不分块，行为不变。
3. **/cost 多一行**：`今天聊天缓存命中 X%（命中 A / 输入 B tokens）`，只统计聊天模型，用真实用量里的 `prompt_cache_hit_tokens`。`python veil_agent.py --cost` 同样显示。

## 没改什么

预算、权限、工具、记忆、长度估算、单步上限、聊天记录格式都没变。不增加模型调用，不改变任何费用上限。

## 未验证

- 没有真实 DeepSeek 数据：命中率提高多少、每天省多少钱，必须看 lan 真实聊天几天后 `/cost` 的数字，**不预先承诺任何比例**。
- 消息中间夹一条 `system` 消息，DeepSeek 接口是否照常接受没有实测（OpenAI 兼容接口通常允许）；如果真实请求被拒绝，会立刻看到“请求失败”，报给 Claude 即可。
- 缓存是 DeepSeek 的自动机制，命中按块、有延迟，具体规则以官方为准；换别家模型要重新看规则。

## lan 验收（Windows，真实 DeepSeek）

1. 照常聊 10 轮以上，输入 `/cost`，看到“今天聊天缓存命中 X%”。
2. 再聊到 25 轮以上（历史窗口满过），再看一次 `/cost`，命中率应在第二个阶段明显不再掉到很低。
3. 聊天回答、记忆、工具照常；如果回复变奇怪（比如不知道当前时间），说一声。
