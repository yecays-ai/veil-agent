# 工单 368：自动整理写入前，先看 Peter 已经存过什么

所属格：A 陪伴 · 记忆。承接工单 364（自动整理）和 363（Peter 自己存记忆的候选流程）。Lan 2026-11-16 定的方向：不加新提示词规则，程序帮 Peter 找到相关记忆，由他判断更新、接续还是新建。

## 起因（已核对）

11-15 同一件事「tool drawers」被存了两次：09:16 Peter 自己存了一条，11:30 自动整理又新建了一条。原因：整理只拿到「它自己最近 12 条」加一次聊天搜索的最多 6 条，Peter 自己刚存的记忆不在里面；整理新建时也没有「接着哪条」的办法（它的写入没有 `link_to`）；两边字数上限也不同（整理 500，Peter 600）。

## 做了什么（`experience_memory.py`，复用现有函数，没有新系统）

1. **候选带真实内容**：每条候选带完整正文、被重写过几次（版本记录条数）、同一经历的其他阶段（新方法 `Memory.experience_stages`，和工单 365 的目录用同一条关联链）。重写权限只给读到全文的候选；太长的（>1200 字）只标「可接续、不可重写」；Lan 锁定的不提供。
2. **候选来源更全**：聊天搜索命中 → 沿同一经历补其他阶段（最多再 4 条）→ Peter 自己最近 3 天存/重写过的最新 3 条（来自 sidecar 的来源记录，不用搜索）。
3. **三种处理**：同一阶段 → `updates` 整段重写；后续阶段 → 新建并填 `continues`（只认给过他的 ID，写入沿用 `link_to` 的同一条 sidecar 关联）；全新 → 正常新建。提示词只多了一句说明和输出格式里的 `continues`，没有加规则。
4. **写入前再查一次**：模型给出新建草稿后，程序用草稿自己的话再搜一遍库；搜到没给过的相关记忆就把它们补进候选再问一次，并把第一次的草稿和「每条草稿搜到了哪些记忆」一起交给他，让他在草稿上修改，而不是重新抽签（第一版真实对比里重新抽签把一次正确的「新建并接续」改成了更新，已改）。最多多一次调用，仍受每日预算约束。再问失败就用第一次的答案，不会因为多这一步漏记。
5. **统一 600 字**：整理的新建上限 500→600。超长不再直接丢掉：告诉模型一次（`last_time_too_long`），让它缩短或拆成后续阶段；仍超长才丢弃并计入。

## 没改的

- Peter 主动存记忆的流程、`hold` 的候选提示、字数上限（本来就是 600）。
- 阈值、Ombre 本身、正式记忆库。「重写时清 digested」等旧记忆整理的事不在这张工单里。

## 找轮子记录

全部复用：`_related` 的同类检索思路、`Sidecar.link/source`、`experience_chain`（工单 365）、`memory-versions.jsonl`、363 的整段重写和版本存档。没有新增依赖。

## 测试

假 Ombre 夹具（`tests/test_experience_memory.py`）：锁定的不提供、过长的只能接续；候选带版本数和其他阶段；Peter 自己最近存的即使搜索没找到也提供并被更新（tool drawers 场景）；草稿命中没给过的记忆→再问一次后更新而非新建；再问失败仍保存第一次的答案；超长只告知一次、缩短后保存；未知 `continues` 被忽略。`tests/test_recall_rotation.py`：`experience_stages` 双向、跳过隐藏、未知 ID 为空。

## 真实模型对比

见 `experiments/experience-368/`（在 Lan 电脑跑，DeepSeek 官方，测试副本，不碰正式库）：11-15 tool drawers 改前/改后，另有正常新建、正确更新、不同阶段接续、新增检索不漏记四项。结果写在 PR 里。

## 验收（Lan）

重启 Peter 后，自动整理触发时：同一件事（Peter 自己刚存过的）不再再新建一条；同一经历的后续阶段出现在记忆页，且能在想起时看到这段经历的目录；锁定的记忆没有被改。
