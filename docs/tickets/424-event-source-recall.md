# 工单 424 · 导入事件和它的旧碎片只算同一次回忆

## 背景

第五步（69 篇正式迁移）在隔离副本上按工单预演时发现：新事件会把它由之整理出来的旧记忆留在同一个
请求里。用事件正文逐个检索 67 个有来源的事件，39 个出现「完整事件 + 旧碎片」同时注入；导入器写的
`event-import-withdrawn.jsonl` 只是一个账本，运行时不读它，也不会归档旧 md。工单要求正式迁移前解决
这个问题，否则停止正式迁移。

## 目标

- 被新事件取代的旧 memory ID 与新事件不再同时进入最终请求。
- 只召回旧碎片时，请求里给的是事件的完整故事，而不是几百字的旧片段。
- 没有被任何事件认领的旧记忆、以及没有事件账本的角色，行为与现在完全一致。
- 不删除、不归档、不改写任何旧记忆文件；旧碎片仍然可以用 `memory_read` 按 id 读到。

## 改法

- `memory_agent.Memory._event_map()`：除事件自己的 `memory_id`，也把事件账本里的
  `source_memory_ids` 映射到该事件。同一个旧记忆被多个事件认领时，按账本顺序取第一个作为故事来源；
  新增 `_event_owners()` 记住全部归属，供去重使用。
- `duplicate()`：用归属集合判断「同一次回忆」，事件有完整故事时才折叠，没有故事的阶段仍各自可读。
- `resolved()`：按本轮真正留下的那个事件取故事，避免一个旧碎片借用已被折叠掉的那个事件的故事。
- 映射按 `events.jsonl` 的 mtime/size 失效：新事件保存后不需要重启进程。
- 没改导入器、没改召回条数／预算／冷却／判官。

## 验证

1. 隔离库 67 个有来源事件：修前 39 个事件与旧碎片同时注入，修后 0；旧碎片单独被召回时
   `items` 里 `event` 有值且 `story: true`。
2. `tests/test_event_source_recall_424.py` 6 条：同时出现、只出现碎片、无主旧记忆、双事件共享碎片、
   账本变更后重读、没有账本时行为不变；在 main 上 4 条失败，修复后全过。
3. 同一组 17 个模块 713 条测试在 main 与修复后都通过。
4. 只读预演本身的数据、备份与证据在 `tmp/step5/`（不进仓库）。
