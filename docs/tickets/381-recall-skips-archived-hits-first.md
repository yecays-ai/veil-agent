# 381 自动想起先去掉已归档的，再取前 3 条

所属格：A（记忆与人格连续性）。做完 lan 能多做的一件事：被整理归档的旧记忆不再白占想起名额，同一话题里本该想起的那一条不会因此被挤掉。她怎么验收：问一件整理过的旧事（普通问法），Recall Memory 里最多 3 条都是现存的记忆，没有「少一条」。

## 现状（真机和实验证据，2026-11-17）
自动想起向 Ombre 要 3 条（`breath_search`，`max_results=3`），之后才由程序去掉已归档/隐藏的。而 Ombre 的检索包含已归档的条目（`search.py` 里 `include_archive=True`），所以排在前三名里的归档条目占了名额，被程序丢掉后不补位。整理旧记忆归档了 40 多条，这条路径随之放大：「你很生气」类题曾因此从 2/2 掉到 0/2（第七批）；「this model keeps ignoring what I tell it」前三名里第 2 名是已归档的 voice pipe，实际只交付 2 条。

根因：「取前 3」发生在「去掉看不见的」之前。同类路径：自动想起的二次检索（短句借上文，`assisted_recall`）也是同样先取后过滤；Peter 自己的 `breath_search` 工具和自动整理的相关记忆查找也是，本单不改（见下）。

## 改动
1. `Memory.context()`：向 Ombre 多要 5 条（共 8 条），先用现有的可见性检查去掉归档/隐藏/来源条目，再取前 3 条。冷却、同一事件去重、名额上限等之后的步骤不变。
2. `assisted_recall()` 的二次检索同样先过滤再取前 3。
3. 不改 Ombre、不改阈值、不补满名额：只有 Ombre 本来就返回了可见的候选，才会递补；没有就保持少于 3 条。
不改：Peter 自己调用的 `breath_search` 工具（`memory_native._search`）、自动整理的相关记忆查找（`experience_memory`），它们用法不同，不属于自动想起。

## 验收（lan 在 Windows 上做）
1. 更新并重开 Peter。普通问法问一件被整理过的旧事（例如第一次写文件那晚），打开「Recall Memory」：列出的都是现存的记忆。
2. 随便聊几句无关闲聊（吃什么、问天气）：没有比以前更多的旧事被带出来。
