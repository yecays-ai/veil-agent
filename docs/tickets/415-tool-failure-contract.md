# 工单 415：工具失败说清真实原因（一个 PR 覆盖整类问题）

- 属于：B 电脑干活（工具用错、失败之后他能不能自己纠正）
- 做完 lan 能多做的事：任何工具失败时，Peter 看得到真实原因和能执行的下一步；她在活动页/回复里看到同一条真实原因，不再是一句「权限拒绝」或一句莫名其妙的话。
- 她怎么验收：见文末三条。

## 目标

建立「失败契约」，并把已知的坏文案一起修掉：每条失败都有真实原因；只有拒绝它的代码本来就知道怎么改时才给改法，不知道就明说；程序内部故障带可追踪错误编号、不冒充他的参数错误，异常原文不外泄；以后再添工具由测试守住，不靠人记得。

lan 要求的三条硬约束（本单按这个做）：

1. 不许按 schema 凭空生成纠错建议。schema 只说明参数格式，不知道失败的真实原因；原始错误必须保留，无法确定怎么修时明确告诉 Peter。
2. 内部异常原文（可能含本机路径、文件内容、凭据）不进模型、不进活动账本。只给安全说明和可追踪的错误编号，原文留在本机。
3. 历史账本不能回溯补写原因；验收只看修复后新产生的记录。

不做的：不逐条重写一百多个工具的失败文案（只修已知问题 + 统一出口兜底）；不增加模型调用；不动权限、审批、预算、记忆和工具清单。

复查后补（同 PR）：统一出口对所有失败兜底（没改法就说没给，不编造）；遍历全部工具 Schema 的探针测试；参数先脱敏再截断。

## 当前状态

- `_execute_tool_call` 是模型工具调用的唯一出口：主聊天、自主醒来、delegate、MCP 四条路径都经过它；`windows_observer`、`windows_interaction`、`tools_agent` 的失败文案各自手写，有的不回显收到的参数，有的把内部异常说成参数错，有的把参数错说成服务不可用。
- `veil_agent` 把工具内部的 `ValueError/TypeError` 一律报成「arguments are not a valid JSON object」（409 遗留），真实原因被掩盖。
- 活动页把 `被拒绝` 一律显示成「权限拒绝」。
- 已发生的证据：11-20 23:30、11-21 01:17、11-21 11:47 三次 `peek_screen`/`snooping_around` 被拒，账本里只有 `参数无效。 This tool does not accept arguments.`，他不知道自己传了什么、也不知道该怎么改。

## 验收步骤

1. 让他把「看前台」带上参数（例如把窗口 id 传给 peek_screen）：回复里的工具行应是「被拒绝」+ 真实原因 + 他传的参数 + 怎么改；活动页展开看到同一条，不再写「权限拒绝」。
2. 让他做一件参数写错的事：他按提示自己改对，不再原样重试。
3. 看 `data\<角色>\tools.jsonl` 最后几行（只看修复后新产生的记录）：失败那条 detail 里有原因、收到的参数（有的话）、怎么改（知道的话）；程序内部故障那条是 `工具内部故障（err-xxxx）`，看不到本机路径；对应原文只出现在 `data\<角色>\tool-errors.jsonl`。
