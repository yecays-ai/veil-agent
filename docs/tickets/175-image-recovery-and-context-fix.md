# 工单 175｜紧急修复：失败图片重启后自动发送 + 上下文长度误拦截

**分支：** `ticket/175-image-recovery-and-context-fix`  
**状态：** 施工中 / 待验收  

## 一、目标

彻底终结失败图片在退出重启后的自动复活重发，消除单张正常图片被聊天历史或记忆挤爆的误拦截，确保同一发送失败只提示一次。

## 二、核心实现

1. **消息生命周期与重启恢复安全（`veil_agent.py`、`web_agent.py`）**：
   - 为持久化消息流转建立明确的状态闭环：`received`（已接收未处理）、`processing`（正在处理）、`committed`（已成功提交）、`failed`（已明确失败）、`cancelled`（已取消/新会话作废）、`uncertain`（服务异常中断待核对）。
   - `TooLong`、请求预检拒绝、媒体失效或未提交异常时，强制将请求 ID 写入 `failed` 终态。
   - `Hub.finish_media_submission` 在 `committed=False` 时调用 `fail_incoming` 终结该请求，杜绝悬挂的 `received` 状态。
   - `start_new_conversation`（新对话）自动作废上一会话所有未提交请求（标记为 `cancelled`），确保新对话绝不继承旧会话失败或残留图片。
   - 重启恢复 `recover_uncommitted_incoming` 严格过滤已失败、已取消、已提交或状态不确定的记录；若崩溃时处于 `processing`，记录 `uncertain` 审计日志，坚决不向 `hub.inbox` 自动投递产生旧消息。

2. **单图上下文预检与多级裁剪容纳（`veil_agent.py`）**：
   - 彻底优化上下文裁剪次序与深度：
     - 发送新图片时，自动将历史记录中的所有旧图片坍缩为文本占位符（`[Lan sent a photo]`），杜绝历史多图重复占用每张 4096 tokens 视觉预留。
     - 逐轮裁剪最旧聊天历史；
     - 若历史已裁剪完毕仍超限，按需逐条裁剪长期记忆召回（`recalled`）；
     - 若仍超限，按需裁剪非关键运行辅助上下文（弹幕历史、近期经历、短期便签、背景注入等）。
     - 坚决保留必要核心：角色身份（Persona）、必要状态与权限（Changing facts）、工具定义与用户当前输入（含图片）。
   - 若即使裁剪全部历史与辅助上下文后仍真实超限（如配置极限过小），抛出包含透明 tokens 分项（系统人设、工具定义、用户输入等）的明确诊断，不再给出模糊的缩短图片提示。

3. **错误提示去重与分类呈现（`desktop/chat.js`、`web_agent.py`）**：
   - 区分后端拒绝、模型失败、上下文超限与网络不确定四类失败。
   - 前端通过 `displayedErrorRequests` 与 `displayedEventIds` 追踪已展示请求与事件，同一请求和失败事件严格只渲染一次，杜绝轮询或重放导致的重复刷屏。
   - 去除“（重复 n 次）”的文本追加逻辑，保持界面简洁整洁。

## 三、Windows 实机体验验收步骤

### A. 失败图片不得复活
1. Lan 选中一张普通图片并点击发送。
2. 模拟或触发发送失败（如极小上下文或网络中断），界面明确提示失败原因。
3. Lan 放弃该图片，转而继续发送普通文字与其他内容正常聊天。
4. 完全退出 VEIL 客户端与后台服务。
5. 重新启动 VEIL。
6. 开始新聊天并发送文字。
7. 旧图片不得自动出现、不得自动提交，也不得进入 Peter 的后续模型请求中。

### B. 重启恢复安全
1. 检查 `incoming-submissions.jsonl`，确认已失败或已取消的消息保留终态记录。
2. 异常中断下未确定的消息仅记录 `uncertain` 审计，重启后不会自动产生对话气泡。
3. 原有历史聊天记录与已成功图片数据完整无缺。

### C. 正常图片发送
1. 在拥有正常长历史和长期记忆的日常会话中，选中一张正常单张图片发送给 Peter。
2. 上下文合理自动裁剪多余历史与记忆，图片成功送达 Peter。
3. Peter 能实际识别图片内容并作出准确回应。

### D. 错误提示去重
1. 制造一次明确的发送失败。
2. 保持聊天窗口运行并等待事件轮询。
3. 界面仅显示一次对应的失败提示，不重复刷屏，不显示“重复 n 次”。
